## Security findings

### 1. Outbox worker bypassed the delivery-start fence

`packages/kratt-core/src/postgres-outbox-store.mjs` already implements `beginOutboxDelivery`, using the same task-scoped PostgreSQL advisory lock as cancellation and checking the lease, intent and `kratt_cancelled_tasks` state. The original `outbox-worker.mjs` claimed a row and invoked the provider adapter directly without calling this fence. A cancellation could win after claim while the worker still proceeded to a provider call.

**Fix:** the worker now requires `beginOutboxDelivery` at composition time and calls it after claim but before `adapter.dispatch`. A cancelled task, stale lease, uncertain prior start, duplicate start or fence-store failure suppresses the provider call. A duplicate start is reconciliation-only, never authorization to call the provider again.

### 2. Unknown provider outcome could be recorded as failure

A timeout or invalid response after the external call began is not proof that the provider performed no side effect. The worker now uses `retrySafety: UNKNOWN` after start, moving the outbox to `RECONCILE` instead of blind retry. If provider success is received but outcome persistence fails, the worker returns `OUTCOME_UNRECORDED` and does not retry.

### 3. Synchronous authorized-dispatch had the same missing fence

`createAuthorizedDispatchRuntime` previously called the provider directly after durable intent commit. It now requires `commandStore.beginAuthorizedDelivery`, obtains a 256-bit opaque delivery token, and only then calls the provider. The token is held inside the server composition root and is required by `appendOutcome`; it is not passed to the provider.

The SQLite command store persists one immutable delivery-start row per idempotency key and an append-only `dispatch.delivery_started` audit entry inside `BEGIN IMMEDIATE`. The same transaction checks task cancellation and the committed intent. `cancelTask` refuses cancellation after a delivery-start record exists. A second start is denied.

After a provider timeout or invalid result, the command store appends `dispatch.reconcile_required` and leaves the intent unresolved. It does not record a false `FAILED` outcome and it does not permit a second provider start. An operator must reconcile the external side effect before any future action.

## Worker state ordering

1. `claimOutbox` reserves a lease; this is not permission to perform an external effect.
2. Resolve an explicitly registered provider adapter. Missing adapter is handled before the delivery fence and may be safely retried because no external effect began.
3. `beginOutboxDelivery` obtains the task cancellation/lease fence.
4. Only `{ ok: true, duplicate: false }` permits one adapter invocation.
5. Provider response must have an allow-listed terminal shape.
6. A verified success is recorded with `finishOutbox`; unknown result/timeout moves to `RECONCILE` with no blind retry.

## Test coverage authored

- Unit tests assert exact call order `claim → begin → dispatch → finish`.
- Cancellation at the fence, lost lease, prior delivery start, duplicate start and fence database failure all assert zero provider calls.
- Provider timeout and malformed response assert `retrySafety: UNKNOWN` and reconciliation.
- A success followed by outcome-store failure is `OUTCOME_UNRECORDED`, never `RECORDED`.
- Direct authorized dispatch tests assert no provider call if delivery start is denied or unavailable.
- SQLite tests assert atomic one-time start, append-only start records, cancellation-before-start denial, cancellation-after-start refusal, delivery token binding, unknown-outcome reconciliation and restart recovery: a fresh store instance cannot start the same delivery again after the prior start record was committed.
- PostgreSQL reliability integration test composes the real worker with the real outbox store: it claims a row, commits task cancellation before `beginOutboxDelivery`, and asserts the provider call count remains zero and the outbox becomes `CANCELLED`.

## Known residual boundaries

- The delivery-start fence orders cancellation against the first possible provider call; it cannot guarantee exactly-once external effects. Stable idempotency keys are still mandatory at provider boundaries.
- A process crash after durable delivery start but before the provider call may leave a conservative reconciliation record. It must not be reset automatically.
- Provider success followed by process crash before durable outcome remains an unknown state for operator reconciliation.
- The SQLite command store is single-host only. Multi-host deployments require shared transactional storage and the PostgreSQL outbox fence.
- WP-03.9 does not perform a production-grade provider credential review because no real provider credential integration is configured.
