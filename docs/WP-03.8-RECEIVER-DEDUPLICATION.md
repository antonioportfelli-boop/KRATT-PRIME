# WP-03.8 — Receiver-side deduplication and durable ACK

Status: implementation committed to `feature/wp-03-8-receiver-dedup-2026-11-26`; PostgreSQL 16 and GitHub Actions execution evidence is still pending verification. Draft PR #60 is open against the Wave 3 feature branch.

## Implemented

### Durable receiver receipt

`0008_fabric_receiver_receipts.sql` adds `kratt_fabric_receiver_receipts`, one immutable terminal receipt per accepted inbox event. The row binds event ID, source and destination nodes, source sequence, SHA-256 event digest, event type, source revision, signing key, policy revision, terminal outcome, serialized handler result, and processing time.

`kratt_fabric_inbound_acknowledgements` stores signed ACK documents per `(event_id, delivery_attempt)`. A repeated request for the same attempt returns the stored ACK. A later transport attempt may receive a new ACK bound to that attempt, while retaining the original business result.

Database triggers reject receipt and ACK mutation/deletion, bind receipts to the immutable inbox row, and reject ACKs whose source node, receiver node, sequence, digest, policy revision, or outcome does not match the durable receipt.

### Receiver transaction behavior

`receiveSteelFabricEventV1` now:

1. Authenticates the Fabric envelope and resolves receiver policy before persistence.
2. Locks and checks existing inbox identity before executing business logic.
3. Returns the persisted result for an exact replay; it never invokes the handler twice.
4. Fails closed on a changed event digest/identity, missing legacy receipt, or changed receiver policy revision.
5. Runs the handler with the transaction client and serializes its result (maximum 1 MiB).
6. Persists the terminal receipt and, when configured, the signed ACK in the same transaction as the inbox and local business writes.
7. Commits before the caller sends the ACK over transport.

If receipt or ACK creation fails, the transaction rolls back. This includes business writes made through the supplied transaction client. Handlers must not perform external side effects directly; those must be represented by a separately governed transactional outbox.

### Signing helper

`createFabricReceiverAcknowledgement` requires an ACTIVE receiver signing identity, creates an ACK bound to event identity and delivery attempt, computes the contract digest, validates the ACK schema, and verifies the Ed25519 signature against the resolved public key before returning it.

The receiver adapter enables durable ACK creation by supplying `deliveryAttempt` and `createAcknowledgement` dependencies. Without an ACK signer callback, the receiver still stores the durable business receipt, but returns no signed ACK.

## Tests authored

The PostgreSQL integration test applies migration 0003 and 0008 twice in an isolated schema and uses two independent pools. It now covers:

- First processing and durable handler result.
- Exact replay of the same attempt returning the same stored ACK.
- A later delivery attempt receiving a distinct signed ACK, then replaying that exact ACK.
- Cryptographic authentication of the returned ACK.
- Rejection of the same event ID with a changed digest.
- Concurrent identical deliveries with a single business handler execution and one ACK per attempt.
- Handler failure retry.
- ACK signing failure rolling back inbox, receipt, and handler writes, followed by a successful retry.
- Database append-only enforcement and rejection of an ACK with a mismatched receiver identity.

Test file: `packages/kratt-core/test/postgres-fabric.integration.test.mjs`.
