# WP-03.8 — Receiver-side deduplication and durable ACK

Status: implementation and CI verification completed on HEAD `7a78789d50ee668e51e1a7ae6a3dd8ab087b2fa4`. Draft PR #60 is open against the Wave 3 feature branch.

## Implemented

### Durable receiver receipt

`0008_fabric_receiver_receipts.sql` adds `kratt_fabric_receiver_receipts`, one immutable terminal receipt per inbox event that reaches a durable terminal processing outcome (`ACCEPTED` or `REJECTED`). The row binds event ID, source and destination nodes, source sequence, SHA-256 event digest, event type, source revision, signing key, policy revision, terminal outcome, serialized handler result, and processing time.

`kratt_fabric_inbound_acknowledgements` stores signed ACK documents per `(event_id, delivery_attempt)`. A repeated request for the same attempt returns the exact stored ACK, retaining its original result (`ACCEPTED`, `DUPLICATE`, or `REJECTED`). A later transport attempt for an accepted event receives a newly signed `DUPLICATE` ACK while retaining the original business result. If the task has already been cancelled, the receiver commits a terminal `REJECTED` receipt and a signed `REJECTED` ACK without running the business handler; later attempts remain `REJECTED` and are never promoted to success.

Database triggers reject receipt and ACK mutation/deletion/truncation, bind receipts to the immutable inbox row, and reject ACKs whose event ID, ACK ID, source node, receiver node, sequence, digest, policy revision, or result does not match the durable receipt.

### Receiver transaction behavior

`receiveSteelFabricEventV1` now:

1. Authenticates the Fabric envelope and resolves receiver policy before persistence.
2. Locks and checks existing inbox identity before executing business logic.
3. Returns the persisted result for an exact replay; it never invokes the handler twice.
4. Fails closed on a changed event digest/identity, missing legacy receipt, or changed receiver policy revision. An exact persisted replay may still retrieve its saved ACK after the event's original TTL; an expired event that has never been accepted is rejected before processing.
5. Runs the handler with the transaction client and snapshots its result without invoking getters/proxies before serialization (maximum 1 MiB).
6. Persists the terminal receipt and, when configured, the signed ACK in the same transaction as the inbox and local business writes.
7. Commits before the caller sends the ACK over transport.

If receipt or ACK creation fails, the transaction rolls back. This includes business writes made through the supplied transaction client. Handlers must not perform external side effects directly; those must be represented by a separately governed transactional outbox.

### Cancellation and trust-revocation fences

Task-scoped `factory.task.*` and `task.*` events must resolve a valid task ID (by the supplied resolver or signed `payload.task_id`). Before first-time business execution, the receiver takes the same PostgreSQL transaction advisory lock used by the KRATT outbox cancellation path (`pg_advisory_xact_lock(hashtext(task_id))`) and checks `kratt_cancelled_tasks` under `FOR UPDATE`. This establishes a single ordering boundary: cancellation-first blocks ingress; ingress-first holds the task lock through handler, receipt, ACK and commit, after which cancellation may proceed. A replay of an already committed event still returns its saved result/ACK and does not re-run the handler merely because the task was later cancelled.

`createPostgresFabricTrustRegistry` exposes `lockInboundAuthorization(client, ...)`. It uses the same `fabric-trust-policy:<source>:<destination>:<event-type>` advisory lock as policy replacement and holds `FOR SHARE` locks on the source node, destination node, source signing key, all currently usable destination signing keys (`ACTIVE`/`VERIFY_ONLY`), and active policy through receiver commit. Source or receiver node disable/revision change, source or destination signing-key revocation/rotation, and policy replacement therefore serialize against a new event's business transaction. The receiver re-runs the authorization predicate against this locked policy and fails closed if the decision or revision changed.

The registry also exposes `lockReceiverSigningIdentity(client, nodeId, keyId, acknowledgement, nowMs)`. The receiver calls it after building or loading an ACK and before committing/returning it. It locks the exact signing-key row and receiver node with `FOR SHARE`, then verifies that an `ACTIVE` key is within its signing window or that a `VERIFY_ONLY` key signed the ACK before retirement and is still inside its verification window. This protects against a race where a key is revoked between signature generation and ACK commit.

### Signing helper

`createFabricReceiverAcknowledgement` requires an ACTIVE receiver signing identity, creates an ACK bound to event identity and delivery attempt, computes the contract digest, validates the ACK schema, and verifies the Ed25519 signature against the resolved public key before returning it. When replaying a persisted ACK, the receiver resolves the exact key ID from that ACK and verifies the historical signature. `ACTIVE` keys are accepted within their signing window; `VERIFY_ONLY` keys are accepted only for ACKs issued no later than retirement and within the configured verification window. `REVOKED` keys fail closed.

When signed ACK mode is enabled, `receiveSteelFabricEventV1` also requires `lockReceiverSigningIdentity` and `revalidateAuthorization`. Before new task-bound processing it obtains the same PostgreSQL task-scoped advisory lock used by cancellation and delivery-start, then checks `kratt_cancelled_tasks`. It revalidates the source/destination/event/scope policy inside the transaction and rejects a policy-revision change before the handler runs. A stored ACK is not blindly trusted on replay: its digest, binding, exact receiver key identity and permitted historical key state, and Ed25519 signature are verified again before it is returned.

The receiver ingress caller enables durable ACK creation by supplying `deliveryAttempt` and `createAcknowledgement` dependencies. This code slice supplies the API and signing helper; it does not yet wire a live STEEL receiver or activate transport. Without an ACK signer callback, the receiver still stores the durable business receipt, but returns no signed ACK.

## Tests authored

The PostgreSQL integration test applies migration 0003 and 0008 twice in an isolated schema and uses two independent pools. It now covers:

- First processing and durable handler result.
- Exact replay of the same attempt returning the same stored ACK and outcome (`ACCEPTED` remains `ACCEPTED`).
- A later delivery attempt receiving a distinct signed `DUPLICATE` ACK, then replaying that exact ACK.
- A previously processed ACK replayed with its historical `VERIFY_ONLY` key, while a `REVOKED` receiver key is rejected.
- A cancelled task producing a durable `REJECTED` receipt and cryptographically authenticated `REJECTED` ACK without invoking the business handler.
- Cryptographic authentication of the returned ACK.
- Rejection of the same event ID with a changed digest.
- Exact duplicate retrieval after the original event TTL, while rejecting a never-processed expired event.
- Concurrent identical deliveries with a single business handler execution and one ACK per attempt.
- Handler failure retry.
- ACK signing failure rolling back inbox, receipt, and handler writes, followed by a successful retry.
- Database append-only enforcement and rejection of an ACK with a mismatched receiver identity.

Additional fast contract coverage exercises ACK creation, `ACCEPTED`/`DUPLICATE` outcomes, active signer enforcement, and cryptographic self-verification in `packages/kratt-core/test/fabric-negotiation-ack.test.mjs`. The receiver mock in `packages/kratt-core/test/fabric-interoperability.test.mjs` was updated for the new inbox query shape.

PostgreSQL integration test: `packages/kratt-core/test/postgres-fabric.integration.test.mjs`.
