# WP-03.8 — Receiver-side deduplication and durable ACK

Status: implementation in progress. This document is the receiver contract and acceptance gate; it is not evidence that the receiver or STEEL has been modified or tested.

## Objective

Make delivery of one authenticated 3XT-FABRIC/1 event at-least-once safe at the receiver boundary: retries may repeat transport, but the same immutable event must not repeat its business effect. Persist the receiver's ACK so a retry can return the original outcome without rerunning the handler.

## Identity and conflict rules

- Primary event identity: (source_node, event_id).
- Immutable identity binding: destination, source sequence, content digest, event type, and authenticated source key/revision.
- Exact replay: same identity and all immutable bindings; return the stored terminal result and stored ACK. Do not invoke business logic.
- Conflicting replay: same event identity with any immutable binding changed; fail closed, emit a security/audit outcome, and do not invoke business logic.
- Sequence collision: same source and sequence with a different event identity; reject as a source-order conflict.
- Never treat a digest mismatch as a duplicate.

## Atomic receiver transaction

After authentication and policy validation, perform the following within one database transaction:

1. Acquire a stable per-event lock; a unique constraint remains the final concurrency arbiter.
2. Insert the inbox/idempotency row in PROCESSING with the immutable event binding.
3. If a matching terminal row exists, return its persisted result and ACK; do not call the handler.
4. If a conflicting row exists, reject without calling the handler.
5. Execute the business handler using the same transaction/client. Business writes must roll back if the receipt/ACK cannot be committed.
6. Persist the terminal processing result and signed ACK (or immutable ACK material sufficient to reproduce the exact same ACK) before commit.
7. Commit once. Only after commit may the transport layer send the ACK.

No external side effect may run inside a retryable transaction unless it is represented by a durable, idempotent outbox intent committed in that transaction.

## ACK requirements

- ACK is bound to event ID, source node, destination/receiver, source sequence, event digest, and receiver policy revision.
- ACK is authenticated with the receiver's active signing identity.
- ACK result is terminal and durable: ACCEPTED, DUPLICATE, REJECTED, or UNKNOWN according to the wire contract.
- A duplicate request returns the stored ACK fields and does not mint a new logical receipt.
- ACK send failure does not roll back committed business work; a later retry retrieves and resends the persisted ACK.
- Unknown or conflicting state is never upgraded to success by inference.

## Required concurrency and recovery tests

1. Two concurrent identical deliveries produce one handler execution and one durable receipt/ACK.
2. Same event ID with changed digest or immutable binding is rejected and has zero additional handler executions.
3. Same source sequence with a different event ID is rejected.
4. Crash/rollback before commit leaves neither business effect nor terminal ACK.
5. Commit succeeds but ACK transmission fails; retry returns the exact persisted ACK without rerunning the handler.
6. Duplicate replay after process restart returns the persisted outcome.
7. Cancellation/authorization revocation races are serialized with the receiver's commit boundary.
8. Database constraints remain authoritative when two receiver instances race.
9. Migration applies twice safely in an isolated PostgreSQL schema; rollback procedure is documented and tested without touching production.
10. Tests use independent DB connections and verify handler invocation counts from durable state, not only mocks.

## Safety boundary

No production/staging migration, live network dispatch, worker activation, credential provisioning, or STEEL repository write is authorized by this work package. Keep main untouched and PRs Draft until explicit operator approval.
