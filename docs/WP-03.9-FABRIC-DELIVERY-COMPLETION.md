## Durable identity binding

Migration `0009_fabric_ack_outbox_reconciliation.sql` adds `ack_policy_revision` to `kratt_fabric_outbound_events`. The revision is captured when the authorized Fabric outbox intent is committed and included in the idempotency reservation digest. Replays must match both the persisted ACK policy revision and original request digest.

The ACK store compares the signed ACK with the stored outbound event and outbox:

- receiver node equals the outbound destination;
- source node equals the outbound source;
- event ID, source sequence and event digest equal the immutable outbound event;
- delivery attempt equals the monotonic persisted attempt sequence;
- ACK policy revision equals the revision captured for this outbound intent;
- receiver key ID resolves to the exact trusted receiver node/key row;
- Ed25519 signature and ACK content digest authenticate successfully.

An old outbound row with no captured `ack_policy_revision` is deliberately unbound and cannot be accepted as completed by this path. It must be handled through a separately authorized reconciliation procedure; the migration does not invent a historical policy revision.

## Event, worker and ACK state lifecycle

1. An approved, request-bound intent is inserted with its durable outbox row and signed Fabric event.
2. `claimOutbox` creates a lease and monotonic delivery-attempt identity. A lease alone is not permission to dispatch.
3. `beginOutboxDelivery` obtains the task-scoped cancellation fence and persists the delivery-start marker/token. Only a successful, non-duplicate start permits one adapter call.
4. A lease expiry before delivery start can be reclaimed. An expiry after delivery start becomes RECONCILE; it is not automatically resent.
5. A verified `ACCEPTED` or `DUPLICATE` ACK is durably recorded, the intent becomes `COMPLETED`, and the outbox becomes `DONE` in one PostgreSQL transaction.
6. A verified `REJECTED` or `UNKNOWN` ACK is recorded and audited, but the outbox moves to `RECONCILE`; the intent remains unresolved. Neither outcome is considered successful completion.
7. When cancellation wins before delivery start, intent and outbox become `CANCELLED`. A later validly signed ACK is preserved in `kratt_fabric_late_acknowledgements` with disposition `TASK_CANCELLED_LATE_ACK`; it cannot promote the cancelled intent or outbox to success.
8. An exact replay returns the already persisted ledger outcome. A different ACK for the same outbox attempt or a reused ACK ID is an `ACK_REPLAY_CONFLICT`.

## Lock order and transaction boundary

ACK ingestion follows this order:

1. Obtain the task-scoped PostgreSQL advisory transaction lock.
2. Lock the outbox and intent rows `FOR UPDATE`.
3. Verify immutable outbound event and attempt binding.
4. Lock the exact trusted receiver node/key `FOR SHARE`.
5. Verify ACK policy revision, key status/window, digest and signature.
6. Insert either the normal ACK ledger row or the late-ACK evidence row.
7. Append the ACK audit event and advance the audit hash-chain head.
8. For `ACCEPTED` / `DUPLICATE`, update intent to `COMPLETED` and outbox to `DONE`; for `REJECTED` / `UNKNOWN`, update only outbox to `RECONCILE`.
9. Commit once.

The task advisory lock is shared with delivery-start and cancellation, so those paths have a deterministic order. The database's deferred terminal-pair constraints reject mismatches such as `DONE + INTENT_COMMITTED`, `CANCELLED + COMPLETED`, or `COMPLETED + RECONCILE`. The ACK audit and row updates roll back together if any insert or update fails.

A lost client response after PostgreSQL COMMIT is handled by replay: the second request finds the durable ACK in the ledger and returns its existing result without repeating terminal updates. The integration suite includes a simulated post-COMMIT response loss.

## Database controls

- `ack_policy_revision` has a constrained identifier shape; NULL denotes an unbound legacy event.
- Normal ACK and late-ACK rows bind to the exact outbox, intent, event, source, receiver, sequence, digest, policy revision and ACK JSON document through database INSERT guards.
- `(outbox_id, delivery_attempt)`, ACK ID and content digest are unique in each ledger.
- Normal ACK, late ACK and reconciliation evidence are append-only; UPDATE/DELETE is denied and the ACK ledgers reject TRUNCATE.
- Intent/outbox terminal pair checks are deferred until transaction commit to permit a single atomic state transition.
- The prior migrations `0001` through `0008` are not rewritten. This package adds migration `0009`.

## Security and error classification

The ACK store no longer relies on a static caller-provided policy revision or an unlocked trust-key lookup for its authoritative decision. It snapshots the ACK shape, loads the target event's expected policy revision, locks the exact trusted receiver key in the same transaction, and performs cryptographic verification before persistence.

Important failure codes include `ACK_POLICY_REVISION_UNBOUND`, `ACK_POLICY_REVISION_MISMATCH`, `ACK_EVENT_BINDING_MISMATCH`, `ACK_ATTEMPT_MISMATCH`, `ACK_KEY_UNTRUSTED`, `ACK_DELIVERY_FENCE_MISMATCH`, `ACK_TASK_OR_PROVIDER_BINDING_INVALID`, `ACK_REPLAY_CONFLICT`, `ACK_INTENT_STATE_CONFLICT`, `ACK_OUTBOX_STATE_CONFLICT`, and `ACK_STORE_UNAVAILABLE`. Errors do not include private keys, secrets, connection strings or ACK payload dumps.

## Tests and verification

The updated PostgreSQL ACK integration case covers:

- per-intent policy revision binding and incorrect policy revision rejection;
- correct ACK, duplicate replay, conflicting replay, REJECTED and UNKNOWN outcomes;
- event ID/digest mismatch;
- cancellation-before-start and late ACK preservation without changing the cancelled terminal pair;
- independent PostgreSQL pools replaying the same durable ACK;
- lost client response after server COMMIT and recovery through a fresh pool;
- receiver-key revocation waiting behind the in-flight ACK key lock, then rejecting later ACKs;

The outbound integration case asserts that the policy revision is persisted with the outbound event. The existing worker integration case continues to verify that cancellation after claim but before delivery start causes zero provider calls.

## Remaining limitations and next dependencies

- This does not guarantee exactly-once effects at an external provider. Provider idempotency semantics still need provider-specific evidence before registration.
- A process crash after delivery-start but before the provider call remains conservative RECONCILE; after provider success but before durable outcome persistence also requires operator reconciliation.
- No live provider, live STEEL receiver, staging or production environment is connected or exercised.
- ACK policy revision must be supplied consistently by the trusted outbound-policy / negotiation path and the receiver ACK signer. A mismatched revision fails closed.
- WP-04 must not begin until the final WP-03.9 SHA has successful Node 22 and PostgreSQL 16 checks, plus a reviewed diff and Draft PR update.
